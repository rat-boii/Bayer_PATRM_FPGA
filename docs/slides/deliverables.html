Algorithm (from the paper)

  • Inverse mapping x = b11 u + b12 v + b13, y = b21 u + b22 v + b23
  • Block start by a 3-stage multiply-add, then addition-only stepping
  • Bilinear interpolation, 7 multipliers per pixel, 4-stage pipeline
  • Custom AXI masters: HP0 read, HP1 write, 16-beat bursts, up to 8 reads in flight

Verification on the board

  • Each case: output vs model, last row, 4096 guard bytes, byte counters
  • 3 sizes × 11 transforms (identity, mirrors, rot 5–180°, scaling, combined)
  • PL clock measured: 100.0025 MHz against the ARM timer and the PC clock
  • Regression: 51 simulation items, including injected faults that must fail

Why it works

  • Each colour plane is warped as its own image with shift tp = ((A − I) o + t) / 2, computed in integers on the ARM
  • Reuses the grayscale engine and its prefetch, so it keeps about 1 pixel per clock
  • Cost: about 2× DDR reads, because each pass reads full rows but uses every second pixel
  • Same bitstream also runs grayscale (33/33 bit-exact)
  • Live demo: colour video over Ethernet, 800×480 at about 43–53 fps

Deliverable 3, observation

Why B is slower: memory latency, not computation

1. No prefetch

With rotation, each output row touches many source rows, so the work splits into tiny blocks (1–2 pixels). Option A prefetches the next blocks while computing the current one. Option B fetches each block only when it needs it, so it waits one full DDR round trip per block and the four lanes sit idle.

Evidence: B reads fewer bytes than A, yet on rot37 its read port was busy about 6 % of the time (A: about 52 %). Read stalls were 30–94 % of B's cycles. Batching the reads inside a block made B 2× faster on rotations; fetching across blocks is the missing step.

2. Single-cycle logic limits the clock

B's buffer lookup and fallback search run in one clock: 98 logic levels, 74 ns. At 100 MHz each step must finish in 10 ns. Option A pipelines its long operations and meets 100 MHz. B therefore closes timing only at 11.9 MHz (fails 100 MHz by 46 ns).

Not the FPGA

Option A uses 5.6 % of the LUTs and about 15 % of the DDR bandwidth. B is limited by its own fetch scheme and unpipelined logic, not by the device.

Lesson: parallel compute only pays off when the memory system can keep it fed. Fix (future work): A-style cross-block prefetch, pipelined search logic and more BRAM ports for 16 pixel reads per clock; estimated ceiling about 2–3× Option A on rotations, set by DDR bandwidth.

Summary

What we delivered

  • Grayscale PATRM reproduced: bit-exact on the board, 100 Mpix/s, 3.3–6.8× faster than the ARM, 5 % of the chip.
  • Bayer Option A: the same engine runs four plane passes, about 1 pixel per clock, for only 319 extra LUTs.
  • Bayer Option B: correct on hardware; faster than A per clock without rotation, slower with rotation.
  • Measured comparison of all three: resources, clock, throughput, DDR bandwidth, power.

Key insight

In this kind of image processing, memory access is the bottleneck, not computation. Option A wins because it inherits PATRM's prefetch; Option B shows that four parallel lanes need a memory system and pipelining designed to keep them fed.

Next steps

  • Cross-block prefetch and pipelining for Option B
  • ARM Bayer baseline for a Bayer speedup figure
